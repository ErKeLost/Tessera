Tessera Studio 当前使用 Mastra 运行 Data Agent。Mastra 是产品内部的 Runtime Dependency，
不是要求用户在自己应用里另外接线的 Tessera Adapter。

## Agent Loop

Tessera 创建一个 Mastra `Agent`，集中注册数据库 Tool、Request Context Processor、呈现
Processor 与本地 `Memory`。同一次 Turn 的所有模型 Step 都由这个 Agent 负责，包括 Tool
Continuation，以及数据库写操作获批后的恢复执行。

```ts
const agent = new Agent({
  id: "tessera-data-copilot",
  model,
  memory,
  tools: databaseTools,
  inputProcessors,
  outputProcessors,
});

const output = await agent.stream(message, {
  memory: {
    thread: threadId,
    resource: resourceId,
    options: {
      semanticRecall: false,
      workingMemory: tesseraWorkingMemoryOptions,
      observationalMemory: false,
    },
  },
  savePerStep: true,
});
```

`savePerStep` 是 Mastra 原生的持久化选项。每个 Generation Step 完成后，Mastra 会把当前
`MessageList` 中尚未保存的消息写入 Memory Store。Tessera 不再在整条 Stream 完成后手工重建
一对 user/assistant 消息，因此 Tool Call、Tool Result 与后续回答不会重复保存。

Observational Memory 保持关闭，因为 Mastra 在启用它时会禁用 `savePerStep`；Semantic Recall 也关闭。
Working Memory 使用 Zod Schema，并设置 `scope: "resource"`、`agentManaged: true` 与
`useStateSignals: false`，因此同一 Resource Identity 的多个 Thread 会按字段 Deep Merge 稳定领域上下文。

Mastra 内部的 `updateWorkingMemory` Tool 仍提供给 Agent，但会从 Tessera 对外 AI SDK Stream 与浏览器
Transcript 过滤。它不是第五个业务 Tool，也不能携带授权或查询 Evidence。

## 两份不同用途的持久化记录

Mastra Memory 是模型私有上下文。浏览器拿到的是另一份经过 Allowlist 与脱敏的 UI Transcript，
其中只包含安全文本、Reasoning 摘要、Tool 生命周期摘要和已验证的 Tessera 分析视图。AI SDK
负责装配 UI Message，Tessera 在每个已完成 Step 后做幂等 Checkpoint。

这条边界既能在刷新后恢复已完成工作，也能防止原始 SQL、Credential、Provider Metadata 与
Query Row 进入浏览器历史。

## 暂停的写操作

数据库写操作使用 Mastra Durable Workflow 的 Suspension 与 `resumeStream()`。持久化的 Workflow
Snapshot 才是审批和恢复的权威状态；UI Transcript 只负责展示，不能授权任何 Effect。
