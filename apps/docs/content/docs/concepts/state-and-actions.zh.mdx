Tessera 不会让同一条 Message Record 成为所有状态的权威来源。每一种状态都有唯一 Owner 与持久化规则。

| 状态 | Owner | 用途 |
| --- | --- | --- |
| 模型对话 | Mastra Memory | 为后续模型 Step 与 Turn 提供上下文 |
| 领域 Working Memory | Mastra Resource-scoped Schema Memory | 跨 Thread 保存稳定偏好与经过验证的可复用分析规则 |
| 浏览器 Transcript | Tessera Session Store | 安全文本、Tool Lifecycle 与已提交分析视图 |
| 本地视图状态 | React Component | Hover、Focus、打开的控件与图表可见性 |
| 审批状态 | Mastra Workflow Snapshot | 持久化 Mutation Suspension 与 Resume |
| 数据库状态 | 已连接数据库 | 权威业务记录 |

## 逐 Step 持久化

Mastra 原生 `savePerStep` 会把已经完成的模型 Step，包括 Tool Call 与 Tool Result，写入私有 Memory。
同时 AI SDK `onStepEnd` 提供已经装配好的 UI Message，Tessera 对它脱敏后保存，用于页面刷新恢复。
重复 Checkpoint 会 Upsert 同一个稳定 Assistant Message ID，而不是不断追加副本。

浏览器 Transcript 不会反过来成为数据库权限来源。原始 Credential、Provider Metadata、私有 Tool
Payload 与不受限 Query Row 都不会保存到其中。

## 分析视图状态

图表 Hover、Focus 与临时可见性设置只由 Renderer 管理。已提交分析视图属于 Assistant Message；
同一 Surface 的累积更新会覆盖之前 Snapshot。本地交互不能修改数据库，也不能虚构新的 Tool Call。

## 数据库操作

读取通过受治理数据库 Tool 执行。写入是类型化操作，并且可以暂停 Mastra Workflow 等待明确审批。
持久化 Workflow Snapshot、Request Identity、Policy Decision 与 Idempotency Key 共同拥有恢复路径；
点击 Client 控件不能绕过这些边界。

## 领域 Working Memory

跨 Session 领域学习使用 Mastra 原生 Resource-scoped、Schema-based Working Memory，并启用
`agentManaged: true`。稳定用户偏好、明确更正，以及由已完成 Evidence 验证的可复用分析规则，会直接
按字段增量 Deep Merge，不增加独立审批流程。每条领域记录都必须有 Scope 与 Provenance。

Raw Row、Query Result、SQL、Schema Snapshot、Secret、PII、权限结论、临时计划、Tool Payload 与猜测
禁止进入 Working Memory。它只是规划上下文，不能授予权限，也不能代替新鲜 Evidence。完整 Schema
与保存规则见[数据上下文与领域记忆](../agent/architecture/data-context-and-memory)。
