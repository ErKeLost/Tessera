---
title: Security Model
description: The trust boundaries around Tessera Agent, connected databases, session memory, and generated views.
---

Tessera treats model output, user text, catalog content, and database values as
untrusted input. Prompts improve behavior, but deterministic server checks own
authorization and execution.

## Database boundary

- Credentials and provider keys remain on the Studio server.
- Every tool has a strict input and output schema.
- Physical reads use validated, bounded SQL and connector-level timeouts,
  cancellation, row limits, and serialization limits.
- Semantic analysis accepts catalog IDs rather than model-authored SQL.
- Metadata output guides planning but cannot prove a requested data fact.
- Database mutations use typed actions, policy checks, durable approval, and
  idempotent resume identifiers.

## Model and presentation boundary

Verified datasets are published only after a database tool succeeds. The
presentation processor can reference those resources and the fixed Tessera
catalog, but it cannot create credentials, URLs, SQL, tools, React components,
HTML, scripts, CSS, callbacks, or executable formulas.

Presentation output is parsed and validated before commit. Unknown recipes,
invalid bindings, malformed values, stale sessions, and failed payload hashes
are rejected. A rejected view cannot execute another query or effect.

## Browser and memory boundary

Mastra Memory stores private model context per completed step. Studio stores a
separate allowlisted transcript for the browser. The browser receives safe UI
message parts and committed, bounded view projections, never database
credentials or unrestricted private tool payloads.

Approval decisions are checked against the persisted workflow snapshot and
request identity. Replayed, stale, or mismatched decisions fail closed.
