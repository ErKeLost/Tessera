---
title: State and Actions
description: How Tessera separates model memory, browser history, local view state, and database effects.
---

Tessera does not use one message record as the authority for every concern.
Each kind of state has one owner and one persistence rule.

| State | Owner | Purpose |
| --- | --- | --- |
| Model conversation | Mastra Memory | Context for later model steps and turns |
| Domain Working Memory | Mastra resource-scoped schema memory | Stable preferences and verified reusable analysis rules across threads |
| Browser transcript | Tessera session store | Safe text, tool lifecycle, and committed analysis views |
| Local view state | React components | Hover, focus, open controls, and chart visibility |
| Approval state | Mastra workflow snapshot | Durable mutation suspension and resume |
| Database state | Connected database | Authoritative business records |

## Step persistence

Mastra's native `savePerStep` writes completed model steps, including tool calls
and tool results, into private Memory. In parallel, AI SDK `onStepEnd` provides
the assembled UI message that Tessera sanitizes and checkpoints for refresh.
Repeated checkpoints upsert a stable assistant message ID instead of appending
copies.

The browser transcript is not fed back as database authority. Raw credentials,
provider metadata, private tool payloads, and unrestricted query rows are not
stored in it.

## Analysis-view state

Chart hover, focus, and temporary visibility settings remain inside the
renderer. A committed analysis view is part of the assistant message, and a
cumulative update replaces the previous snapshot for the same surface. Local
interaction cannot change the database or invent another tool call.

## Database actions

Reads execute through the governed database tools. Writes are typed operations
that may suspend a Mastra workflow for explicit approval. The persisted
workflow snapshot, request identity, policy decision, and idempotency key own
the resume path; clicking a client control cannot bypass them.

## Domain Working Memory

Cross-session domain learning uses Mastra's native resource-scoped, schema-based
Working Memory with `agentManaged: true`. Stable user preferences, explicit
corrections, and reusable analytical rules verified by completed evidence are
deep-merged incrementally without a separate approval flow. Every domain entry
is scoped and carries provenance.

Rows, query results, SQL, schema snapshots, secrets, PII, permission decisions,
temporary plans, tool payloads, and guesses are forbidden. Working Memory is
planning context and cannot grant authority or replace fresh evidence. See
[Data Context and Domain Memory](../agent/architecture/data-context-and-memory)
for the complete schema and save rules.
