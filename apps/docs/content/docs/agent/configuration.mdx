---
title: Configuration
description: Configure Tessera Studio, its database boundary, and model runtime.
---

Tessera reads one server-only `tessera.config.ts`. The configuration owns the
database connection, semantic definitions, model settings, and Studio network
boundary. Generated analysis views are built into Studio and have no separate
installation or public configuration block.

```ts
import { defineTesseraConfig } from "@open-tessera/studio";

export default defineTesseraConfig({
  database: {
    url: process.env.DATABASE_URL!,
    schemas: ["analytics"],
    maxRows: 5_000,
    statementTimeoutMs: 30_000,
  },
  llm: {
    model: "openrouter/qwen/qwen3.8-27b",
    reasoningEffort: "low",
    temperature: 0.1,
    maxOutputTokens: 12_800,
    maxSteps: 50,
    maxRetries: 0,
  },
  studio: {
    host: "127.0.0.1",
    port: 4317,
    catalogCacheTtlMs: 60_000,
  },
});
```

## Database

`database.url` is required. The URL determines the dialect unless an explicit
matching `database.dialect` is provided. `schemas` narrows discovery for
PostgreSQL and MySQL. `maxRows`, `statementTimeoutMs`, and `permissions` bound
what the Agent can execute.

Turso credentials use `database.authToken` or `TURSO_AUTH_TOKEN`; keep the token
separate from the database URL.

## Model

Model IDs use Mastra's `provider/model` form. Tessera can read common provider
keys from server environment variables, or accept `llm.apiKey` directly in the
server-only config. `llm.baseUrl` and `llm.headers` support compatible gateways.

`maxSteps` bounds the complete model/tool loop, while `maxRetries` controls
provider retries. Presentation validation has its own bounded processor retry
and does not add a tool to the Agent.

## Studio network boundary

Studio binds to loopback by default. A non-loopback host requires all of the
following:

- `studio.allowRemote: true`
- authentication enabled
- at least one explicit `studio.allowedOrigins` entry

This prevents a local database workspace from becoming remotely reachable by
accident.
