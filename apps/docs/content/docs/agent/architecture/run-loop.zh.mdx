---
title: 运行循环
description: 从澄清请求到发布回答的显式、可中断分析循环。
---

运行控制器负责一个用户可见的状态机：

```text
澄清 → 发现 → 规划 → 查询 → 验证 → 综合 → 发布
              ↑         ↘ 修订 / 重试 ↗
```

## 1. 澄清

统一指标、粒度、维度、比较窗口、时区和预期决策。只有当歧义会实质性改变查询或回答时，
才向用户提问。将假设记录在运行状态中，并在对话界面中展示。

## 2. 发现

检索相关的语义定义、获准数据集、Join 关系、新鲜度和已有的限定范围上下文。
对一小组上下文进行排序，不要把整个目录塞进模型 Prompt。

## 3. 规划

选择有界工具序列，并设置成本、时间、行数和重试预算。可见计划可以包含操作摘要、前置条件和状态，
但不得暴露隐藏思维链。

只有同时满足以下条件时才使用 Worker：

- 子问题可以独立完成；
- 结果可以通过类型化契约合并；
- 并行执行能显著降低延迟或提高召回率；
- 控制器仍负责验证并拥有最终回答。

## 4. 查询

生成结构化工具参数，使其通过策略和权限检查，然后以稳定的幂等标识符和 Trace 标识符执行。
在审批或长时间任务前持久化检查点。

查询执行只有一个数据边界。语义工作使用
`search_data_context -> prepare_analysis -> execute_sql(analysisRef)`；显式 SQL 使用
`list_database -> execute_sql(sql)`。Semantic Catalog 与准备阶段都不访问 Row。Insert、Update、
Delete 与 DDL 进入 `execute_sql` 的类型化 Mutation 分支，由服务端完成风险分类与审批。完整契约见
[数据上下文与领域记忆](./data-context-and-memory)。

## 5. 验证

语法层面的查询成功是必要条件，但并不充分。验证 Schema、行数限制、总计、空值、时间边界、单位、
新鲜度、核对关系和统计假设。验证失败时向控制器返回简洁的修复信号，并消耗一次有界重试。

## 6. 综合

只根据经过验证的输出构造论断。在起草时附加证据 ID，区分观测事实与解释，并说明重要限制。
不得从相关性推断因果关系，也不得仅根据可见点估计推断统计显著性。

## 7. 发布

在同一回答中发布正文、Tool 状态、Evidence 引用与可选生成式分析视图。视图保持声明式，
不能执行模型编写的代码，也不能再次查询数据库。

## 失败与中断

每个阶段都把状态写入持久运行状态。取消信号会传播到数据仓库查询和 Worker。可重试错误会保留
已经完成的证据；权限拒绝和审批失败会停止当前分支，而不会被当作普通工具故障。
