# 商业化扩展：独立 App 与生成式 UI

现有产品已经拥有管理端 Dashboard、业务数据、用户身份和权限。新的商业化能力可以沿两条路线扩展：

- **方案 A：生成独立 App**：根据客户提供的数据和操作入口，生成一个由我们托管、再嵌入客户已有应用的独立应用。
- **方案 B：生成式 UI**：在现有 Dashboard 或 AI 对话中，直接生成一个可以查询和交互的工作界面。

## 方案 A：生成独立 App

### 核心方式

我们不读取客户原产品源码，也不修改客户原系统。客户提供数据库、REST/OpenAPI、SDK 或其他受控数据接口，我们根据数据契约和业务需求生成新的 App。这个 App 有自己的运行时、发布和版本，但最终通过 iframe、反向代理路径或微前端方式嵌入客户已有应用。

```text
客户提供数据、操作和身份集成接口
  -> 建立数据、权限、SSO 和 UI 契约
  -> AI 生成页面、交互、数据适配器和服务端逻辑
  -> 构建 -> 预览嵌入效果 -> 用户审阅
  -> 发布并嵌入客户已有应用
```

生成的 App 属于我们，客户原产品继续作为数据和身份来源。它可以拥有独立版本和运行时，但用户感知上应该是客户已有应用中的一个页面、菜单项或工作区。

### 嵌入和集成要求

#### 嵌入方式

| 方式 | 特点 | 适合阶段 |
|---|---|---|
| iframe + 统一入口 | App 与客户系统隔离，接入最快；需要处理高度、自适应、跨窗口消息和 CSP | MVP 和大多数客户交付 |
| 反向代理路径 | 通过客户域名下的 `/apps/...` 访问，URL 和网络体验更统一 | 对域名和安全策略有要求的客户 |
| 微前端 / 组件集成 | 视觉和交互最自然，但需要统一前端运行时、依赖和发布节奏 | 高价值、深度集成客户 |

第一阶段建议使用 iframe 或反向代理。微前端不应该作为默认方案，因为它会把客户的前端构建、依赖和发布约束引入我们的交付链路。

#### 单点登录和身份

独立 App 不能要求用户再次登录。至少需要约定：

- 客户应用通过 OIDC、SAML、企业身份代理或一次性短期 Launch Token 把用户带入 App；
- App 服务端根据验证后的身份建立自己的 Session，不接受浏览器直接传入的用户 ID 作为授权；
- 客户用户、组织、租户、角色和我们的 App 用户之间有稳定映射；
- Token 只用于登录交换，不写入 URL、前端存储或生成的 UI；
- 退出登录、Session 过期和权限变化可以同步回客户应用；
- 高风险写操作仍由 App 服务端重新检查权限，不能因为用户已经完成 SSO 就默认拥有全部 App 权限。

#### 权限模型

需要把客户原应用权限和新 App 权限分成两层：

1. **入口权限**：客户应用决定用户是否能看到和打开这个 App。
2. **业务权限**：App 服务端决定用户能读取哪些数据、执行哪些 Action，以及每个租户的范围。

客户可以通过角色、Scope 或授权 API 提供初始权限，但 App 必须在每次数据读取和写操作时做服务端校验。不能只在菜单层隐藏入口，也不能把 `tenantId`、`role` 或 `ownerId` 当作浏览器传来的可信字段。

#### UI 样式和体验

独立 App 如果完全使用自己的设计系统，嵌入后会像一个外部网站。交付前需要约定：

- 客户品牌色、字体、圆角、间距、阴影、图标和暗色模式；
- 客户导航、面包屑、页面标题和返回路径；
- iframe 的宽度、高度、响应式断点和移动端行为；
- 加载、空状态、错误、权限不足和登录过期页面；
- 主题切换、语言、时区和日期货币格式；
- 通过 CSS Variables、Theme Token 或设计 Token 适配客户样式，而不是让模型自由生成 CSS。


### 适用场景

- 客户需要一个长期使用的运营工作台；
- 需要嵌入已有应用，同时保持独立发布和版本管理；
- 需要统一的单点登录、角色权限和品牌样式；
- 需要复杂表单、流程、审批、异步任务或多系统编排；
- 需要把生成结果交付给客户，作为正式产品或增值模块；
- 客户不开放源码，但可以提供稳定的数据和业务 API。

### 优点

- 生成结果可以长期沉淀、版本化和发布；
- 适合复杂业务逻辑和定制化体验；
- 运行时接近普通 Web App，长期成本更可控；
- 可以独立定价、按客户交付和管理生命周期；
- 页面、权限、数据契约和测试都可以审阅。
- 可以在不修改客户原产品源码的情况下独立迭代。

### 缺点

- 生成、构建、预览和发布耗时更长；
- 需要维护 App 生成、构建、版本和发布系统；
- 代码生成质量需要测试和人工审阅；
- 客户必须提供稳定的数据契约和业务接口；
- 需要额外建设嵌入、SSO、权限映射、主题适配和跨应用通信；
- 客户原应用的 CSP、Cookie、网络和安全策略可能影响交付；
- 并发修改、版本冲突、回滚和兼容性治理更复杂。

## 方案 B：现有 Dashboard 内的生成式 UI

### 核心方式

AI 不生成一个独立项目，而是在当前 Dashboard 或对话区域内生成受限的 UI 程序。UI 使用现有组件、查询和操作能力，直接展示实时数据。

```text
用户描述需求
  -> AI 生成 UI 结构和交互
  -> Dashboard 校验并渲染
  -> 查询实时数据
  -> 用户筛选、刷新和触发操作
  -> 继续对话修改当前界面
```


### 适用场景

- 管理端临时分析、报表和运营视图；
- 用户希望根据问题快速生成 KPI、表格、图表和筛选器；
- 需要快速验证需求，不希望每次都构建和发布新 App；
- 不同角色需要不同的工作视图；
- 作为正式 App 生成前的原型和需求发现工具。

### 优点

- 反馈速度快，用户几乎可以即时看到结果；
- 适合探索和反复调整；
- 可以直接复用现有 Dashboard、Agent、数据权限和登录体系；
- 不需要为每个需求创建独立项目和部署流程；
- 可以按用户、角色、工作区或套餐提供生成能力。

### 缺点

- 适合结构化查询和交互，不适合复杂业务系统；
- 组件和交互能力受 UI 组件库限制；
- 每次查询、刷新和交互都会产生运行时成本；
- 必须严格限制 UI、Query 和 Mutation 契约；
- 生成结果容易成为一次性视图，需要额外设计保存、共享和版本能力；
- 不适合作为完整 App 的长期替代品。

## 方案对比

| 维度 | 方案 A：生成独立 App | 方案 B：生成式 UI | 哪个更优 |
|---|---|---|---|
| 主要结果 | 一个独立、可发布的 App | 当前 Dashboard 中的交互视图 | A：长期产品；B：即时视图 |
| 数据前提 | 客户提供稳定数据库、API、SDK 或数据契约 | 使用现有 Dashboard 已连接的数据和权限 | B：接入成本更低 |
| 是否需要客户源码 | 不需要 | 不需要 | 两者相同 |
| 生成内容 | 页面代码、数据适配器、服务端逻辑、测试 | UI 结构、查询、交互和状态 | A：生成范围更宽 |
| 生成 UI 复杂度 | 可以覆盖完整页面、复杂流程、多角色和多系统编排 | 适合组件库内的页面、查询和轻量交互 | A：复杂度和自定义强度更高 |
| 交付速度 | 分钟到小时 | 秒到分钟 | B：更快 |
| 是否需要构建发布 | 需要 | 通常不需要独立部署 | B：流程更短 |
| UI 自由度 | 高 | 受组件库限制 | A：更强 |
| 业务复杂度 | 适合复杂流程和多系统编排 | 适合查询、分析和轻量操作 | A：承载能力更强 |
| 数据交互 | 通过 App 服务端 API / Repository | 通过 Dashboard 的受治理数据接口 | B：复用现有能力更简单 |
| 写操作 | App 业务 API 和服务端权限 | 受控 Mutation、审批和操作接口 | A：适合复杂写流程 |
| 数据分析 Agent | 可按 App 需求接入 Agent，但不是默认能力 | TOB 数据分析必须配备专有数据分析 Agent，负责语义、指标、权限、查询和证据 | B：数据分析场景必须专有 Agent |
| 嵌入方式 | iframe、反向代理或微前端 | 直接在现有页面组件树中渲染 | B：集成更简单 |
| 单点登录 | 需要 OIDC/SAML/Launch Token 和 Session 映射 | 直接复用现有登录 Session | B：身份链路更简单 |
| 权限复杂度 | 入口权限、App 权限、租户和角色需要双向映射 | 复用现有 Dashboard 身份和权限，再限制生成式 Tool | B：权限复用更简单 |
| UI 样式 | 需要 Theme Token、容器适配和视觉验收 | 直接复用现有组件库和设计系统 | B：视觉一致性更好 |
| 跨应用通信 | 需要 postMessage、事件协议或宿主回调 | 使用页面内状态和现有数据接口 | B：通信成本更低 |
| 用户体验 | 嵌入在已有应用中的长期工作区 | 对话旁边的即时工作界面 | A：长期工作区；B：即时反馈 |
| 保存方式 | App 项目、Revision、Release | View、Thread、Message 或模板 | A：正式资产能力更强 |
| 运行成本 | 发布后接近普通 App | 每次渲染、查询和交互持续消耗运行资源 | A：长期运行成本更低 |
| 版本管理 | 代码版本、构建版本、发布版本 | UI 程序、数据绑定和视图版本 | A：版本治理更完整 |
| 回滚方式 | 回滚 App Revision 或 Release | 恢复旧视图或 UI 版本 | A：回滚能力更完整 |
| 商业化方式 | 独立 App、客户定制、模块和高级套餐 | AI 工作区、生成次数、查询预算和视图模板 | A：客单价和交付范围更高 |
| 集成复杂度 | 高：嵌入、SSO、权限、主题、网络和版本兼容 | 低到中：主要是 Tool、渲染和数据预算 | B：集成复杂度更低 |
| 主要风险 | 代码生成质量、嵌入和身份集成、发布治理 | 数据越权、查询成本和 UI 契约膨胀 | A：工程风险更高；B：运行时风险更高 |
| 最适合的阶段 | 需求已经稳定，需要正式交付 | 需求探索、快速试用和即时分析 | B：前期验证；A：成熟交付 |
